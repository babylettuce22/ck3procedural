# Who the rite's guest list is allowed to offer.
#
# ---- What a guest invite rule actually is ----
#
# Not a filter. A BUILDER. The planner shows one tab per rule the activity declares, and the
# tab's contents are whatever the rule's `effect` block put in the `characters` list -- so a
# rule cannot narrow the guest list, it can only produce one. That is why the trait test
# appears here as a `limit` on each iterator rather than as a condition somewhere central:
# every route into the list has to carry it, because each route is its own gathering.
#
# It is also why this file is only half of the answer. A rule that adds nobody but members
# still leaves the OTHER routes into an activity -- events, effects, a future rule someone
# adds without reading this -- unguarded. The hard gate is `can_be_activity_guest` in
# 00_society_rite_activity.txt, which the engine checks for every candidate however they got
# proposed. Belt and braces, and vanilla's witch ritual wears both for the same reason.
#
# ---- Why these iterators and not `every_living_character` ----
#
# Because you cannot invite someone you have never heard of. There is no world-wide roster in
# this prototype -- when the generator writes a real society it will keep one, as a global
# list maintained at game start, and these rules become a single walk over it. Until then the
# reachable sets below are both the honest answer and the cheap one: a ruler's court, his
# vassals, his family, his spouses and his liege are the people he could plausibly know the
# allegiance of.
#
# `bannable_serving_diarch_trigger = no` is copied from every vanilla invite rule. A serving
# diarch cannot leave, so offering one is offering a name that will always decline.
#
# =====================================================================================
#  TWO rules
# =====================================================================================
#
# This was one combined rule for a while and is now two. An earlier version of this note
# claimed the split was a FIX -- that a single entry left the guest window with no tabs and made
# the rite unstartable. That was wrong. The guest failure had a separate cause and a separate
# fix; the number of rules was never the problem, and nothing here should be read as evidence
# that the engine requires more than one category.
#
# The split is kept because it is better, not because it repaired anything:
#
#   - It is the shape vanilla uses for the analogous activity. The witch ritual, the only
#     shipped activity that gates a guest list on a trait, declares two rules
#     (house_witches, other_witches) rather than one combined list.
#   - Court and Elsewhere are a real distinction to a player deciding who to expose to whom.
#   - They are separately diagnostic. If one tab fills and the other does not, the empty one
#     names the iterator that found nobody, with no scaffolding needed to find that out.
#
# ---- The debug_log lines ----
#
# `debug_log` is a legal effect in an invite rule and writes to debug.log, which is the only
# way to see a count the tab does not show. An empty tab has four possible causes -- rule never
# ran, ran and matched nobody, matched people who were then vetoed by can_be_activity_guest, or
# the planner declined to draw an empty tab -- and the UI distinguishes none of them. One line
# at the top of an effect says it ran; one inside an iterator counts what it proposed.
#
# They cost a line in a log nobody reads unless something is wrong. Removing them prematurely is
# what turned the last round of this into three cycles of re-reading script that was fine.


# =====================================================================================
#  Sworn in our court
# =====================================================================================
#
# The household. In practice this is where the first few members come from, because the
# induction interaction is easiest to use on somebody already standing there, and it is the tab
# that should never be empty once society.9001 has been pressed.
activity_invite_rule_society_court = {
	effect = {
		debug_log = "SOCIETY: court invite rule running"

		every_courtier = {
			limit = {
				has_trait = society_member
				bannable_serving_diarch_trigger = no
			}

			debug_log = "SOCIETY: court rule proposing a sworn courtier"

			add_to_list = characters
		}
	}
}


# =====================================================================================
#  Sworn elsewhere
# =====================================================================================
#
# Everybody else this ruler could plausibly know the allegiance of. Blood is in here rather than
# in the court rule because it crosses realm borders where vassalage does not -- it is the
# nearest thing this prototype has to the cross-realm reach a society is supposed to have, and
# it is the half a world-wide roster will eventually replace.
activity_invite_rule_society_abroad = {
	effect = {
		debug_log = "SOCIETY: abroad invite rule running"

		# Downward through the realm.
		every_vassal_or_below = {
			limit = {
				has_trait = society_member
				bannable_serving_diarch_trigger = no
			}

			debug_log = "SOCIETY: abroad rule proposing a sworn vassal"

			add_to_list = characters
		}

		every_close_or_extended_family_member = {
			limit = {
				has_trait = society_member
				bannable_serving_diarch_trigger = no
			}

			debug_log = "SOCIETY: abroad rule proposing sworn kin"

			add_to_list = characters
		}

		every_spouse = {
			limit = {
				has_trait = society_member
				bannable_serving_diarch_trigger = no
			}

			debug_log = "SOCIETY: abroad rule proposing a sworn spouse"

			add_to_list = characters
		}

		# Upward. `?=` because a top-level ruler has no liege and the engine should not be asked
		# what trait nobody has.
		liege ?= {
			if = {
				limit = {
					has_trait = society_member
					bannable_serving_diarch_trigger = no
				}

				debug_log = "SOCIETY: abroad rule proposing a sworn liege"

				add_to_list = characters
			}
		}
	}
}
